# Specification — submitted input in the transcript

**Status:** proposed specification for human review. This document is the complete input to the later **transcript 000**, **transcript 001**, … checkpoint series. It assigns no implementation work by itself. Checkpoints belong in `checkpoints/`, one per later conversation.

Every completed input is a retained presentation immediately above the results it causes. A click can restore a Python form or colon command to the editor, or repeat a menu action. History remains bounded and contains live objects, not reconstructed source values.

## 1. Boundary and preserved behavior

This extends the implemented [listener](../listener/spec.md), [listings](../listings/spec.md), [REPL](../repl/spec.md), [chips](../chips/spec.md), and [SymPy](../sympy/spec.md) designs. It changes history recording, the three new input presentations, and their click and menu behavior only. The ten colon commands, command parsing and exact-type accept, Python `compile_command` and execution, chip splicing and cleanup, `_`, captured output, error formatting, listing redisplay, SymPy printing and `simplify`/`expand`/`factor`, and existing object menus keep their rules. An input presentation is not a `Value` and is not accepted as a file, directory, process, or listing target. Do not synthesize Python source to replay an action.

Use the existing `src/pbui/` package and `tests/`. The headless model and tests must import without Textual; only `pbui.terminal` imports it. Prefer no new dependency. Implementers use the existing uv project: `uv sync` and `uv run pytest`; `uv run pbui` is only for the screen hand check. If uv is unavailable, stop and report it. The designer does not run uv.

## 2. What enters history, and when

Register three distinct presentation types: `PythonInput`, `CommandInput`, and `MenuActionInput`. Their values are immutable records. Each completed attempt gets a *new* presentation, including a run of restored input or a repeated action. Append it before invoking the operation, so all output, values, listings, and errors caused by that attempt follow it in their existing order. It stays even when an operation produces no result row. The history's **500 logical row** limit still applies; every drawn input row counts. Eviction does not rewrite or mutate other presentations.

| Type | Record retained by the presentation | Commit point |
|---|---|---|
| `PythonInput` | The complete ordered lines of text runs and Python chips, with each chip's captured label and **original object by identity**. Never store the generated `_pbui_chip_N` source as the form. | `compile_command` returns code, or raises a compile error for a finished submission. Append before execution or before its one `Error`. |
| `CommandInput` | The text after the dispatching colon, plus an optional command chip's exact presentation type, label, and object. A typed argument remains text; parsing it does not turn this saved input into a chip. | The command attempt is ready to dispatch, including an unknown or malformed command. If a command waits for presentation accept or substring accept, append only when the missing input is supplied and the operation runs. |
| `MenuActionInput` | The chosen action label, resolved operation (including a translator function when applicable), any argument such as the completed `narrow` substring, the target's original object by identity, and a captured one-line target label for drawing. | The action runs. For `narrow`, this is the nonempty Enter that applies it, not the menu choice that opens substring accept. |

A delayed presentation accept stores the command name and the accepted command chip, not a path or pid reconstructed from the chip label. `:rm` followed by a click on a file records `rm` plus that file chip. Yank loads `:rm` and the same chip. Enter runs `rm` on that object. `:show`, `:cd`, and `:kill` follow the same rule for the object that was accepted. Canceling the accept records nothing.

A delayed `:narrow` stores text, not a chip and not a hidden listing. The saved tail is `narrow`, one space, and the substring that was entered. Yank loads `:narrow SUBSTRING`. Enter then uses the current newest-listing rule; it does not seek the listing that was current when the substring was first requested. A menu `narrow` is a `MenuActionInput`, not a `CommandInput`. Its saved target is the listing that was narrowed, and its saved argument is the substring. `run again` applies that substring to that listing.

Do not record empty or whitespace-only input, a bare colon, a Python Enter for which `compile_command` returns `None`, or a canceled continuation or accept. A multi-line Python form gets **one** `PythonInput` presentation only when finished, not a presentation per Enter. A syntax error gets the form followed by one `Error`. An unknown or failed colon command gets the command followed by one `Error`. A translator or menu command failure gets the action followed by its existing `Error`. A command that merely enters accept has not run; cancellation adds no command row. The recording step must not compile, splice, parse, execute, or print the input a second time.

Existing operations that redraw a retained listing in place still redraw it in place. The new command or menu-action row records the operation at the end of history before that redraw; it does not relocate the listing block. A replayed menu action uses its saved target object and resolved operation, even if the original target presentation has since left history. The ordinary domain revalidation and failure behavior still apply. If a listing action needs a listing no longer retained for redisplay, append the action row and one `Error` explaining that the listing is no longer in history; do not silently apply it to another listing.

## 3. Drawing and retained identity

Every logical input row begins with **`› `**. It distinguishes input from result rows without hiding a short form: `› 1 + 2 + 3` appears in full. The marker is drawing, not part of stored Python source or command text. Escape unsafe display characters using the existing safe-display rules. Preserve each chip's editor label: Python chips draw as `⟨LABEL⟩`, and a command chip draws as `⟨TYPE: LABEL⟩`, matching the editor. These brackets are drawing only. A command draws with its leading colon, for example `› :ls`, `› :ls /tmp`, or `› :rm ⟨File: /tmp/a⟩`. The saved command text is the raw tail after the dispatching colon; leading whitespace before that colon is excluded. An optional space immediately after the colon is retained. Restoring these examples yields respectively `:ls`, `:ls /tmp`, and `:rm` plus the same command chip.

A menu action draws its label followed by ` — ` and the captured one-line target history text, for example `› simplify — x*(x + 1)`. A `narrow` action also shows its committed substring after the label, so the recorded action can be understood and repeated. Escape and cap the target label at 96 display cells; this affects drawing only. The action target and argument are kept in full. Neither an input row nor its marker is a `Value` result or an invitation to run `show`.

A Python form preserves source line boundaries. Split long displayed lines into logical history rows at **120 display cells including `› `**, then start another `› ` row; never turn a source newline into the literal `\n` on one row. Draw at most **12 logical rows for one input presentation**. If more rows are needed, draw the first 11 and a twelfth row `› … (N more input rows)`, where `N` is the number of omitted rows. The same presentation spans every visible row, including the cut marker: a click on any of them targets the whole saved form.

A colon command and a menu action each draw as **one** logical row, also capped at 120 display cells including `› `. When the row would be longer, keep the first 119 cells and a final `…`. The captured command chip label remains the editor's existing label, then the row cap applies to the whole drawn line. The menu target label remains capped at 96 cells before it is placed in that row. Truncation and history eviction never shorten the stored command text, substring, chips, or action target; yank and `run again` use the full saved record. Existing viewport layout may further wrap a logical row at the terminal width, and every physical segment remains hit-testable as that same presentation.

## 4. Click, editor, and menu routing

Use a fresh innermost hit and the existing first-left-click rule. An open menu handles its click first; presentation accept and substring accept handle theirs next. They retain exact-type acceptance and current cancellation behavior. Input presentations are inert accept targets. Ctrl-O and button 3 still open the menu of the hit object when menus are allowed. Hover stays ordinary reverse-video hover during Python composition, never accept-target styling.

At an empty editor with no continuation, accept, or menu, a left click on `PythonInput` loads its saved lines and chips into the Python editor **without execution**. Previous lines become pending continuation lines and the final line becomes the editable line; a single-line form uses the ordinary prompt. Every chip still contains its saved object, not its displayed label. A left click on `CommandInput` similarly loads the colon, saved tail, and optional command chip into the command editor. Enter, after any edits, is the only way to submit either one. A command chip is supplied by object through the existing command acceptance rules when Enter runs it; incompatible edited commands fail through ordinary command error handling. Submission records a new input presentation ahead of its new results. The source presentation stays in history.

During Python composition, a left click on a `Value`, file, directory, process, or other object-bearing result still inserts one Python chip at a valid expression-atom site under the chips specification. A left click on a `PythonInput` or `CommandInput` inserts that input's saved pieces at the cursor, rather than replacing the work already typed or executing anything. For a command, include its colon and text; convert its saved command chip to a Python chip of the same object and captured label. If a pasted input spans lines, join its first line to the text before the cursor, place intermediate lines in pending source, and join its last line to the text after the cursor. The insertion is one editor change; no compilation occurs on click. The ordinary single-object chip insertion guard remains unchanged for clicks on result presentations.

At the same empty editor, a left click on `MenuActionInput` directly runs its saved operation again on its saved object, records a **new** `MenuActionInput`, then appends or redraws the results in their usual order. It does not fill the editor or invent `simplify(...)` or any other Python statement. During Python composition, clicking that row inserts a Python chip of its target object; it does not run the action. Existing chip insertion-site refusal applies to that chip.

The `PythonInput` and `CommandInput` menus each have exactly one item, `yank`, with the empty-editor load behavior. If invoked while composing, `yank` inserts the saved pieces at the cursor, preserving the current input. The `MenuActionInput` menu has exactly one item, `run again`, with the same direct action behavior as its empty-editor left click. An open menu, accept, or substring accept continues to take priority over all of these routes. Menu actions invoked during Python composition preserve pending pieces and cursor as existing menus do; a `narrow` action retains its current suspend-and-restore behavior.

With no higher-priority modal state, the exact documentation sentences on these history presentations are:

| Target and mode | Documentation line |
|---|---|
| Python form, empty editor | `Click to load this Python form into the editor; Enter runs it.` |
| Colon command, empty editor | `Click to load this command into the editor; Enter runs it.` |
| Menu action, empty editor | `Click to run “LABEL” again on the same object.` |
| Python form or colon command, composing Python | `Click to insert this input at the cursor.` |
| Menu action, composing Python, valid chip site | `Click to insert this action's target into the expression.` |

For a menu-action target at an invalid Python chip site, use the chips specification's exact string/comment or other invalid-site sentence. When the input's menu item is hovered, use `Click to yank this input into the editor.`; for the action's item use `Click to run “LABEL” again on the same object.` Replace `LABEL` with the captured action label. Existing no-target, continuation, accept, and open-menu documentation keeps its precedence. Recompute documentation when editor mode changes without pointer movement.

## 5. Verification and slice order

Keep all older tests passing. Headless tests, with no Textual, must demonstrate `1 + 2 + 3` appending its form before the `Value` holding `6`; yank restoring the same pieces and chip objects without evaluation; an incomplete continuation adding nothing and its completion adding exactly one form; a syntax error adding that form before one `Error`; `:ls` adding its command before listing rows; an unknown and a failed command adding a command before `Error`; and `simplify` adding an action before the new SymPy expression while leaving the source expression intact. Cover command text versus command-chip restoration, `:rm` followed by a clicked file yanking that chip rather than path text, `:narrow` followed by a substring yanking `:narrow SUBSTRING` as text, a multi-line click from any drawn row, truncation restoring the full form, a command or menu row cut at 120 cells whose stored record stays complete, and run-again creating a new action row. Use injected services and temporary roots for command tests.

**Slice 1 — record and restore.** Add the three headless presentation records, commit-point ordering, yank and insertion operations, and menu-action replay, with the headless tests above. Do not import Textual.

**Slice 2 — screen.** Draw marked and bounded input rows; add their hit testing, documentation, clicks, menus, and screen coverage. Preserve the listener 005 row-local hover regression. Run `uv run pytest`. For one hand check, start `uv run pbui` from a recorded disposable directory under the project root: enter `1 + 2 + 3`, see its form above `6`, click the form, edit it, and press Enter; enter `:ls` and see it above the listing; then apply SymPy `simplify` and see the action above the new expression. The original expression must remain.

The human reviews this spec before a checkpoint manager writes **transcript 000**. Pandas, in-place editing of history, new SymPy operations or pretty-printing, a second thread, recording non-submitting keys, and replay through generated Python source are outside this specification.
